# agent-fixes Workflow

> **🚨 Read this entire file before doing anything else — including responding to the user's first prompt.** If your harness truncated it into an "Output too large — saved to: `…/mcp-agent-fixes-onboard-…txt`" file with only a preview shown, open the saved file and read it in full now (paginate with `offset` + `limit` + `unit: "bytes"` via `mcp__agent-fixes__read` if needed).

> **The user can override this — and when they do, follow them.** This startup sequence is the default ordering for when the user hasn't told you otherwise; it does **not** outrank a direct instruction. If the user tells you to do something before or instead of startup — and *especially* if they push back or admonish you for starting up first — do what they said immediately, without re-litigating the order or running startup "to be safe" anyway. Acknowledge, comply, then fold the remaining startup steps in once their instruction is handled.

agent-fixes provides session management, inbox messaging, issue tracking, code exploration/editing tools, and a knowledge system for AI agents. Everything is accessible via CLI (`af` or `agent-fixes`) or MCP tools, and auto-detects the current session either way.

## Required Output Consumption

Running a required grounding command is not the same as reading it. If you redirect, tee, save, or externalize output from `af continuity recall`, `af knowledge init`, `af onboard`, `af tail`, or any user-requested command, you must read the saved content into context before acting on it. AF knowledge commands may also return a `Knowledge Output Externalized` notice when the estimated token count is too large for inline delivery; that saved file is the required output, not an optional attachment. Use MCP/AF read tools with explicit offsets or line ranges and continue until the saved output has been covered. Do not treat exit status, a file path, `wc`, or a visible preview as completion. If you cannot consume the saved output, stop and say exactly what remains unread.

## Startup Sequence (Do This First)

On session start, before any other work:

1. **Call the `whoami` MCP tool** (no arguments) — specifically the MCP tool, not `af whoami` in the shell. The CLI path cannot see Codex's per-call `_meta.threadId`; the MCP request can, and it records that thread id for background inbox/resource delivery.
2. Inbox delivery is automatic via MCP `resource-updated` notifications — no watcher setup needed.

## Code Tools

> **MANDATORY: AF code tools are your PRIMARY tools for all code work.** Do not use grep, rg, find, fd, cat, or Read for code navigation when AF tools are available. This is not a suggestion — it is a hard requirement.

**Codex: use the MCP tools, not the CLI wrappers.** In Codex, "AF code tools" means the loaded MCP tools (`find_symbol`, `symbols_overview`, `find_references`, `search_pattern`, `find_file`, and edit tools). Do **not** run `af code ...` shell commands for code navigation when the MCP tools are available: the CLI wrappers are one-shot processes with cold in-memory caches, while the MCP server keeps the symbol cache warm across calls. The CLI wrappers are for humans or MCP-unavailable fallback only.

**CLI output.** In harnesses without MCP, such as Pi, use the `af code ...` commands without `--json`. The default text output is deliberately structured for agent consumption. Add `--json` only when a program will manipulate the result; do not request "machine-readable" JSON reflexively, since it wastes context without making the result easier for an agent to use.

AF provides tree-sitter-powered code exploration across 14 languages (Rust, Python, TypeScript, Swift, Kotlin, C, C++, ObjC, JSON, TOML, HTML, Markdown, Bash, and more). The tools work on this repo and on external codebases (SDK headers, cargo registry, other repos) — pass an absolute/~/glob path and they'll resolve it.

**Path handling.** All tools take a `path` parameter. Relative paths resolve against the repo root; absolute, `~`, and glob paths are used as-is.

**Tool choice.**

| Instead of... | Use |
| --- | --- |
| grepping for definitions | `find_symbol`, `symbols_overview` |
| grepping for usages | `find_references` |
| `rg` for content search | `search_pattern` (annotates matches with enclosing symbols) |
| `find` / `fd` | `find_file` |

Built-in Read remains appropriate for non-text files (images, PDFs).

**Fallback rule.** If an AF tool fails after 2–3 attempts, you may fall back to built-in tools — but **tell the user** the AF tool failed and why (e.g., "find_symbol returned no results for X, falling back to grep"). If the fallback also fails, switch back to AF with a different query rather than flailing on grep.

### Reading

- **`symbols_overview`** — top-level symbols in a file. Use `depth > 0` to include children. Start here to understand a file's structure.
- **`find_symbol`** — symbols by name across files. `search_mode: "exact"` for precise matches (handles reversed words like `request_approval` → `ApprovalRequest`), `"explore"` for fuzzy. Name patterns: `name`, `Parent/name`, `/exact/path`, `Type/method`, `[N]` for overload index. Set `include_body=true` for source.
- **`find_references`** — references to an identifier with enclosing symbol and context. `call_receiver` shows the object for method calls. Filter with `include_kinds`/`exclude_kinds`.
- **`search_pattern`** — regex search via ripgrep, annotated with enclosing symbols. Supports context lines and `paths_include_glob`/`paths_exclude_glob`.
- **`find_file`** — fuzzy file finder. Use when you don't know the exact path.

### Editing

When MCP tools are available:

- **`replace_content`** — find/replace in a file (literal or regex; `$1`/`$2` for backrefs; `replace_all=true` for multiple).
- **`replace_symbol_body`** — replace a symbol's entire definition by name path. Body must include the signature.
- **`insert_before_symbol` / `insert_after_symbol`** — insert relative to a named symbol. Handles blank-line separation per language.
- **`extract_symbols`** — bulk-move top-level symbols between files: `from_path` + `destination_paths` as `{ "target.rs": ["SymA", "impl SymB"] }`.

Built-in Edit/Write remain appropriate for simple line-level changes or new file creation.

## Knowledge System

AF includes a push-based knowledge system. Projects can have a `knowledge/` directory containing per-chunk `.md` files (with YAML frontmatter) that is delivered automatically to agents when they touch relevant code — no need to remember to read docs. This project does not have one yet; `af knowledge new` can scaffold one if the user wants it. (A legacy single-file `knowledge.html` format is still supported as a fallback for projects that haven't migrated.)

## Issues

Use af issues to track your work. When the user gives you a task, create an issue, start it, and resolve it when done. This is how progress is communicated — to the user and to other agents.

### Granularity

An issue represents a **meaningful unit of work the user would recognize** — a feature, a bug fix, a refactoring, an investigation. Not implementation steps. "Add pagination to the user list" is an issue. "Edit line 47 of api.rs" is not. Test: if you'd describe it to the user as progress ("I finished X"), it's issue-sized.

If real work comes up in conversation — a bug, a missing feature, a design problem — and the user moves on, create an issue before continuing. Don't rely on context to bring it back. Minor observations and cosmetic nits don't need issues — the bar is "would this be a real loss if forgotten?"

### Two patterns

**Standalone tasks** (most issues): one issue, one unit of work.

```
○ agent-fixes.42 Show deleted session names as 'name (deleted)'
```

**Epics with slices** (larger planned work): the parent carries motivation/design/references; children are independently deliverable, commit-sized slices created at planning time.

```
○ agent-fixes.70 Implement Tantivy-based full-text search [13 children]
  ✓ agent-fixes.70.1 Add Tantivy dependency and schema module
  ✓ agent-fixes.70.2 Add search index state table to SQLite
  ✓ agent-fixes.70.3 Implement JSONL line parser for indexing
  ...
```

Slices are **parallel by default**. Numbering is for identification, not execution order. Only use parent/child blocking when one slice genuinely requires another's output.

### Hierarchy = blocking

Parent/child means **blocking**, not categorization. A parent can't close until all children resolve. Create a child when you discover a prerequisite mid-work, or when decomposing an epic into slices. Don't create children for steps within a single coding session, or to group loosely related things.

When working on an issue with open children, complete the children first.

### Titles

Terse, verb-first, outcome-oriented. Describe what changes, not how:

- "Add Tantivy dependency and schema module" — not "Run cargo add tantivy and create schema.rs"
- "Fix tail showing tool calls as user messages" — not "Edit format_line in fmt.rs"

### Lifecycle

```
af issue list                              # your issues
af issue show <id>                         # details, including children
af issue create "title"                    # new top-level
af issue create --parent <id> "title"      # new child
af issue create --for <session> "title"    # for another session (notifies them)
af issue start <id>                        # mark in progress
af issue pause <id>                        # back to open
af issue resolve <id> -m "..."             # done
af issue delete <id> --reason "..."        # cancelled / superseded
af issue reopen <id>                       # reopens closed ancestors too
```

IDs are hierarchical: `<session>.<n>` (e.g. `agent-fixes.7`, `agent-fixes.7.1`). They sort naturally.

**Have one issue in progress at a time** — it's your current focus, not a backlog.

`resolve` and `delete` accept multiple IDs for batch operations. When batch-closing a parent, include all open children in the same call.

**NEVER use `--priority` unless the user explicitly asks.** Hierarchy already conveys blocking; priority is noise. If you want to set priority, it probably wants to be a child issue instead.

**Don't use `--other-agents` unless asked.** Issues created for you appear in your normal `af issue list`.

### Referencing code

Use `path::anchor` syntax — stable across refactoring, greppable. Include enough context to be unique:

```
src/foo.rs::pub fn bar(
src/types.rs::struct Config {
src/lib.rs::impl Handler {
```

## Sessions & Naming

A **session** is a running agent instance. Each has a UUID; it may also have a human-readable **name** assigned via `af save`.

- Session ID alone is enough for `af ps`, `af tail`, `af session search`, `af inbox send/check`.
- A name is **required for all issue operations** — issues are owned by names.

**NEVER run `af save` yourself.** Naming is the user's prerogative. If an issue operation fails with `"actor must be User or Named..."`, tell the user you need a name and let them run `af save`.

Names support history: `my-feature~1` = the previous session that held that name. `af session history` lists them.

```
af session list                  # named sessions
af session ps                    # running processes      (also: af ps)
af session search "query"        # full-text search across transcripts
```

`af ps` carries each agent's work state immediately after its kind: `pi [busy]` means working, `pi [idle]` means idle/free, and `pi [????]` means AF could not determine the state. Filter with `af ps --status busy` or `af ps --status idle`; both retain `[????]` sessions so uncertainty is never hidden. A trailing `[● 1 ○ 2]` summarizes one in-progress issue and two open issues.

### Namespaces

Names support one level of namespacing with `/` (e.g. `transcription/parser`, or `transcription/` for an auto-generated local name).

- **Issues** are shared across a namespace — all `transcription/*` sessions share the `transcription.*` issue space and counter.
- **Inboxes** are per-session — `af inbox send transcription/parser` reaches only that session. Use `af inbox list --namespace` to see namespace-wide.

### Canonical name

Your session has a canonical name only if exactly one registry entry points to its UUID. Zero → issue commands fail (unnamed). Two+ → ambiguous; operations that need your name will error. `af save` also **moves** a name off whoever held it before, so check with `af session get <name>` first if the name might be in use.

### Reading transcripts

`af tail` / `af head` read a session's JSONL transcript. **Omit the identifier to target the current thread** (the session you're running in); otherwise pass a name, UUID, or `name~N`. They fall back to an interactive picker only when no current session resolves. **The default view is chat (user + assistant); pass `-A`/`--all` for the full physical transcript** (tool calls, thinking, system, summaries).

```
af tail                         # current thread, last 10 chat messages
af tail -A -n 50 -f             # include tool/thinking/system lines, tail -f style
af tail my-feature -u -n 40     # another session, user messages only (-a assistant)
af tail \~1                     # the previous session (escape ~ in zsh)
af head                         # current thread, from the start
```

**Compaction periods (`-C`).** `-C` slices the transcript by compaction boundary: `-C` / `-C 0` = from the most recent compaction to now; `-C 1` = the period just before that; `-C N` = N periods back (no compactions → whole file). So `af tail -C 1` reads this thread's messages from before the last compaction.

For the **current** session after a compaction (when earlier context is gone), `af head` reads from the start. Role filters and `-A` work on `head` too, and `-n` counts after filtering.

The MCP `tail` tool mirrors all of this: omit `identifier` for the current thread, `roles` defaults to chat, and `roles: ["all"]` returns everything.

**Catch-up via byte cursor.** Every tail ends with a footer like `[cursor session=<uuid> offset=1847293]`. That offset is the byte position after the last raw JSONL line consumed — stable as the file grows. To read only what arrived since your last check, pass it back:

```
af tail worker -n 20
# ... footer: [cursor session=abc offset=1847293]

af tail worker --after-offset 1847293
# only new lines since last tail; footer updates to the new offset
```

MCP equivalent: `tail({ identifier: "worker", after_offset: 1847293 })`. Negative line numbers (`-1`, `-2`, …) still address the end of the file but drift when new lines append; use the cursor for incremental catch-up, not `-L`.

### Search

`af session search` queries a Tantivy index across transcripts. Supports booleans (`AND`, `OR`, `+`, `-`), phrases (`"exact"`), field targeting (`user:query`, `tool_result:"..."`), time filters (`--since`, `--until`, `--today`), and modes (`--mode session|message`, `--scope chat|all`, `--order best|latest|earliest`, `--literal`, `--substring`).

By default it scans **every session file on disk** (named or not). Pass `--named` to restrict to registered (named) sessions when you only care about ones the user explicitly saved.

Use `tail` when you know which session to inspect; use `search` to find which session discussed something. When the user says tail, tail — don't reach for search as a shortcut.

### File activity

`af session files <name-or-uuid>` scans that session's transcript on demand and reports transcript-visible file reads, writes, search scopes, and unresolved shell effects. `--json` returns the full evidence model. Each access is labelled `confirmed`, `attempted`, `inferred`, or `failed`; history copied into a fork is reported separately as inherited. The MCP `session_files` tool returns the same report.

## Inbox

Agents message each other via inbox:

```bash
af inbox send other-agent "Question about the API" -b "optional body"
af inbox check                   # See pending messages (marks delivered)
af inbox list                    # All messages
```

Schedule delivery for later instead of sending now — deferred reminders to yourself (send to your own session name) or recurring pokes to another session:

```bash
af inbox send <to> "Review PR" -b "..." --at "in 2 hours"   # one-shot; natural-language time
af inbox send <to> "Standup"   --every "30m"                # recurring interval (2h, 30m, 1d)
af inbox send <to> "Sweep"     --cron "0 0 9 * * 1"         # 6-field cron: sec min hour dom month dow
```

`--at` accepts natural language ("thursday 9am", "tomorrow 3pm", "in 2 hours").

Inbox is **push-based** - Claude hooks and Codex `resource-updated` deliver messages automatically. Don't poll manually unless you're expecting something specific.

Issue notifications (create for another session, resolve, delete) automatically send inbox messages.

## Plans

## Remote Agents

Create and control external Claude Code or Codex sessions as remote agents.

### Create

```bash
cd ~/repos/amar/target-repo && af create --claude --no-connect namespace/task-name
cd ~/repos/amar/target-repo && af create --codex  --no-connect namespace/task-name
```

**Always `cd` into the target directory in the same shell command as `af create`.** Do not set `cwd` separately — the child needs `cd` to fire direnv, rust-toolchain, and other directory-triggered env setup. Always pass `--claude` or `--codex`. Name sessions using a namespace matching the work (check `af list` for existing ones).

After creation, the session sits at the welcome screen. Send it a task with `af session send`.

### Send and steer

```bash
af session send <name> "Your prompt here"
af session send-keys <name> enter        # required after send for multiline
af session send <name> "CORRECTION: do X instead"
af session screen <name>                 # verify steering was absorbed
```

`send` pastes text into the terminal; `send-keys enter` submits it. Mid-work corrections are queued until the next turn boundary. Run tool calls sequentially when targeting the same session — parallel sends can interleave.

### Completion

Creating, prompting, or inbox-messaging a session records lineage and arms semantic `finished` supervision automatically. Pi children publish authoritative operation evidence; legacy terminal agents use the Petty compatibility producer. A Pi child that yields with a pending wake remains unfinished without interrupting its parent, then settles after the resumed turn. Running Petty work without a registered wake is independent and does not withhold finishing. The terminal outcome is delivered with the response or failure diagnostics and MCP `resource-updated` wakes Codex. Do not add another completion watch for a normally tracked child. Explicit `af.finished` watches are for non-lineage interest and require a backstop that only wakes the watcher for inspection—it never stops the target.

### Read results

```bash
af session last-response <name>          # final assistant text (primary)
af session last-exchange <name>          # final user/assistant chat exchange
af session since-last-user <name>        # includes tool calls and results
af session screen <name>                 # current visible terminal
af tail <name> --chat -n 10              # last 10 user/assistant messages
```

Use `last-exchange` when you need the prompt context plus the answer: it returns the final contiguous block of user messages and any assistant messages after it. Use `last-response` when only the final assistant text matters; use `since-last-user` when you need tool/result noise too.

### Interrupt / slash commands / lineage

```bash
af session send-keys <name> escape escape   # stop current operation — NEVER ctrl+c
af session send-command <name> /compact     # slash commands (also: af session compact <name>)
af tree                                     # your session's child tree
af lineage mark-permanent <name>            # exclude long-running agents from automatic supervision
```

### Rules

- **Puppeteer yourself** — don't delegate remote agent control to a subagent. You have the context; a subagent two steps removed does not.
- **Steer, don't kill** — rarely exit sessions.
- **Compaction is destructive.** Check token count via `af session screen` first. Opus 4.6 has a 1M window; 600–800K is NOT near the limit. Only `/compact` at 950K+ or on context-related failures. If the model silently switched to Sonnet (200K), fix the model — don't compact.

# Petty execution and universes

Petty is AF's terminal execution substrate. It owns named PTYs, terminal state,
scrollback, raw output cursors, lifecycle, durable watches, process cleanup, and
iroh QUIC endpoints. Local and remote traffic use the same
remoc/MessagePack protocol; there is no Unix-socket compatibility plane.

## When to use it

Use Petty for builds, tests, checks, servers, benchmarks, interactive programs,
and any work whose duration is uncertain or which may need later observation,
input, interruption, or independent lifetime. A blocking shell is for bounded
inspection and genuinely short one-shots.

```bash
petty run build -- cargo build        # task session; returns after dispatch
petty attach shell                    # interactive session; create or join
petty list                            # host-wide inventory
petty info build                      # full metadata
petty snapshot shell                  # current ANSI screen
petty history build                   # retained output
petty tail build                      # retained + resumable live output
petty send shell 'echo hello'
petty send-keys shell 'ctrl+c enter'
petty kill build
```

Detach from an interactive attach with `Ctrl+\`; detaching does not kill the
session. `petty list` is deliberately compact; use `petty info` for full node IDs
and argv.

Transport silence is not lifecycle evidence. `stale` and `unavailable` never
mean dead, never authorize replacement, and never settle supervision. Positive
wrapper/child state, explicit control, or an opted-in lease deadline does.

## Watches: terminal evidence, not duplicate agent supervision

```bash
petty wait build
petty watch build task_complete --id build-complete
petty watch server session_exit --id server-exit
petty watch shell screen --pattern 'ready' --id ready
petty watch shell output --pattern 'READY' --id future-ready
petty watches build
petty receipt build build-complete
petty ack build build-complete
```

Watches are durable, incarnation-pinned, and resumable after transport loss.
Receipts survive wrapper teardown until acknowledged. `screen` is
level-triggered and includes terminal echo; `output` observes future raw bytes
from the armed cursor. A retention gap or rebaseline is explicit.

AF automatically tracks created children and exact prompt/inbox operations.
Messages create one-shot FINISH interest, never lineage. Do not add `petty_wake`,
`af.idle`, or a second completion watch for normal operation settlement. Petty watches are for
non-agent terminal work or deliberately additional/non-lineage observation.

## Pi ownership

Pi's structured `petty` tool is ownership-filtered. Runtime-owned work dies with
the Pi runtime; session-owned work can be reclaimed by the conversation;
detached work deliberately outlives Pi. Raw `petty list` is the host-wide
namespace.

After dispatching uncertain-duration terminal work, arm `petty_wake` and stop
polling. `task_complete` is the normal recipe for `petty run`; `session_exit` is
for the enclosing session lifecycle. A backstop wakes the watcher for
inspection; it does not time out, cancel, or fail the target.

## Native remote filesystem and foreground tools

Pi exposes Petty universes as first-class tools rather than making agents
construct CLI commands or transport encodings:

- `petty_read`, `petty_write`, and `petty_edit` mirror the ordinary local file
  operations while adding a `universe`; binary content uses explicit base64
  fields and images arrive as native attachments.
- `petty_stat`, `petty_list`, `petty_mkdir`, `petty_remove`, `petty_rename`, and
  `petty_copy` operate directly on the same filesystem plane.
- `petty_exec` runs literal argv through fixed stdin/stdout/stderr and returns
  separate output lanes plus authoritative exit/signal status.

Remote filesystem paths are absolute. Use these tools directly: do not create a
temporary mirror, shadow checkout, Python wrapper, base64 shell pipeline, or
hand-built `petty file` command. `petty_exec` is for bounded foreground work;
uncertain-duration work remains a named `petty` run plus `petty_wake`.

## Universes and remote addressing

A Petty universe is a remote session namespace with stable authority and an
elected gateway role. Remote targets have the `session@universe` shape.
Ordinary wrappers elect the gateway through a persistent
`flock`; there is no daemon. The gateway resolves names and authorized spawn
requests, then the client dials the session endpoint directly.

AF embeds that directory on AF's already-elected endpoint instead: the AF endpoint
is the universe endpoint and its single router serves only AF control and Petty
directory. Its stable service key is addressed directly through Petty's universe
aliases; Petty owns machine admission, reachability aliases, provisioning
invitations, and upstream registration. AF does not mount or announce through a
second registry. AF does not enable Petty's standalone gateway election or
`universe.toml`; after AF resolves an agent, terminal
traffic still dials the returned Petty wrapper directly. AF control deliberately
uses the same trusted machine-client capability as Petty attach/input/kill: a
key admitted to this machine can perform both semantic and terminal
administration. AF does not add a separate per-operation grant architecture.

```bash
petty universe add dev-amar <gateway-public-key>
petty universe add lab '{"id":"...","addrs":[...]}'
petty universe list

petty info shell@dev-amar
petty attach shell@dev-amar
petty tail shell@dev-amar
petty send shell@dev-amar 'cargo test'
petty wait build@dev-amar
```

Aliases are human input sugar. Programmatic state uses canonical universe keys.
All ALPNs require pinned-key admission; loopback is not a trust bypass.
Reachability is declared in `universe.toml`, not widened by environment
variables.

Remote execution has two explicit capability paths. A peer granted open-spawn
authority can execute native argv directly:

```bash
# Bounded foreground command: relay I/O and return its exit code.
petty exec dev-amar --cwd /work/app -- cargo test

# Independently supervised task: dispatch under a remote name.
petty run build@dev-amar --cwd /work/app -- cargo build
```

Use an explicit absolute cwd for repository work. `exec` is for bounded
foreground commands. Use a named `run` task for uncertain-duration work, choose
its Pi ownership deliberately, arm one `task_complete` wake, and do not poll.

Peers without open-spawn authority can invoke only declared profiles with
bounded parameters and fixed argv/cwd/environment shape:

```bash
petty spawn build@dev-amar --param repo=/work/app
```

If neither open-spawn nor a suitable profile is granted, surface the missing
capability rather than tunneling around policy.

## Resuming a named AF session

To give an existing named AF session a running instance without attaching the
caller, run this on the machine that owns its AF store:

```bash
af resume --no-connect <name>
```

This preserves the existing underlying agent identity. `af create <name>@<universe>`
creates a new identity; `af resume <name>@<universe>` resolves the existing AF
identity and never falls back to creation or repoints the name.

AF performs the semantic resume through its control protocol, then returns the
canonical Petty target so terminal traffic goes directly to the wrapper:

```text
AF resolve/create/resume → af:<session-id>@<canonical-universe-key>
                         → direct Petty attach/screen
```

AF names belong to the remote AF store. New launches use the canonical PTY name.
When resolving sessions created by older AF versions, AF checks every historical
PTY alias and returns the live authoritative wrapper; Petty never reinterprets
AF registry aliases itself.

## Provisioning and machine authority

Published reachability and authority are separate. A bare published key can be
the ordinary provisioning/registration reference, but publication grants no
trust by itself. Provisioning grants OpenSpawn only to the one authenticated
upstream key on the joining machine; it does not grant the joining node authority
over upstream or create anonymous access. Signed invitations add bounded
namespace/quota/rate/profile and posture constraints.

Normal agent work uses an already-configured alias and does not provision,
invite, pledge, trust, or alter registration policy unless the task explicitly
owns machine admission. Safe inspection is `petty universe list`, `petty trusted`,
`petty registrations`, and `petty authority <universe>`. Provider SSH is
break-glass for a host whose Petty installation is unavailable, not a substitute
transport or bootstrap authority.

## Full Petty reference

The Petty repository's `USAGE.md` is the command-oriented reference for local
sessions, universes, files, forwarding, provisioning/repair, registration,
invitations, posture, trust, declared spawn profiles, cursor continuity,
watches, receipts, and leases.
